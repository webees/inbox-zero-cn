title: '图片代理'

---

Inbox Zero 可以代理远程电子邮件图片和 CSS 加载的资源，使发件人在邮件渲染时看不到最终用户的 IP 地址。

这是可选的，但如果你为其他人托管 Inbox Zero，则推荐启用。

## 它的作用

启用后：

- 远程 `img`、`srcset`、`background`、`poster`、内联 `style` 和 `<style>` 资源 URL 会在渲染时被重写。
- 浏览器会从你的代理加载这些资源，而不是直接从发件人控制的宿主加载。
- iframe 渲染器还会应用严格的 CSP，因此即使重写器遗漏了某种情况，直接远程获取也会被阻止。

代理是与主应用分离的服务。应用会为代理 URL 签名，由代理获取上游图片。

## 部署到 Cloudflare Workers

仓库在 [apps/image-proxy](https://github.com/elie222/inbox-zero/tree/main/apps/image-proxy) 中包含一个可直接部署的 Worker。

### 1. 登录 Cloudflare

```bash
cd apps/image-proxy
pnpm exec wrangler login
pnpm exec wrangler whoami
```

### 2. 创建签名密钥

在 Worker 和 Web 应用中使用相同的密钥：

```bash
openssl rand -hex 32
```

### 3. 设置 Worker 密钥

```bash
cd apps/image-proxy
pnpm exec wrangler secret put IMAGE_PROXY_SIGNING_SECRET
```

### 4. 无需编辑任何仓库文件即可部署

将 `img.example.com` 替换为你自己的主机名：

```bash
cd apps/image-proxy
pnpm exec wrangler deploy --domains img.example.com
```

这是推荐的自托管路径，因为它无需仅为选择域名而编辑 `wrangler.jsonc`。

### 5. 配置 Inbox Zero 应用

在你的应用环境中：

```bash
NEXT_PUBLIC_IMAGE_PROXY_BASE_URL=https://img.example.com/proxy
IMAGE_PROXY_SIGNING_SECRET=your-generated-secret
```

这些值必须匹配：

- `NEXT_PUBLIC_IMAGE_PROXY_BASE_URL` 告诉应用将代理资源请求发送到哪里。
- `IMAGE_PROXY_SIGNING_SECRET` 必须与 Worker 密钥匹配，以便代理验证已签名的 URL。

如果你需要为不同客户端使用不同密钥，请为每个签名方配置各自的单一 `IMAGE_PROXY_SIGNING_SECRET`，并为代理验证器配置逗号分隔的列表。
示例：

```bash
# web app signer
IMAGE_PROXY_SIGNING_SECRET=server-secret

# desktop app signer
IMAGE_PROXY_SIGNING_SECRET=desktop-secret

# proxy validator
IMAGE_PROXY_SIGNING_SECRET=server-secret,desktop-secret
```

## 未签名自定义代理模式

如果你设置了 `NEXT_PUBLIC_IMAGE_PROXY_BASE_URL` 但没有设置 `IMAGE_PROXY_SIGNING_SECRET`，Inbox Zero 会发出未签名的 `?u=` 代理 URL。

该模式仅适用于有意接受未签名请求的自定义代理。当设置了 `IMAGE_PROXY_SIGNING_SECRET` 时，内置的 Cloudflare Worker 期望已签名的 URL。

生产环境推荐使用签名模式。

## AWS 选项

如果你不想使用 Cloudflare，仓库还在 [apps/image-proxy-aws](https://github.com/elie222/inbox-zero/tree/main/apps/image-proxy-aws) 中包含一个 AWS Lambda 适配器。

部署模型为：

- 部署 Lambda
- 在其前面放置 CloudFront
- 将 `NEXT_PUBLIC_IMAGE_PROXY_BASE_URL` 设置为你的 CloudFront URL
- 使用相同的 `IMAGE_PROXY_SIGNING_SECRET`

## 自托管 Next.js 选项

如果你正在自托管并希望获得最简单的设置，Inbox Zero 可以通过其自身的 Next.js 应用路由代理远程图片，而不是使用单独的服务。

设置以下应用环境变量：

```bash
NEXT_PUBLIC_IMAGE_PROXY_USE_APP_ROUTE=true
IMAGE_PROXY_SIGNING_SECRET=your-generated-secret
```

在此模式下，Inbox Zero 会为图片代理 URL 签名，并将它们路由到 `${NEXT_PUBLIC_BASE_URL}/api/image-proxy`。

说明：

- 这运行在主应用进程中，因此更简单，但隔离性不如单独的代理服务
- Next.js 路由使用与 AWS 适配器相同的 SSRF 保护，包括 DNS 解析和固定公网地址查询
- 请保持设置 `IMAGE_PROXY_SIGNING_SECRET`；没有它，生产环境的 URL 重写将保持禁用

## 故障排查

### 健康检查

部署后，这应返回 `200`：

```bash
curl -I https://img.example.com/health
```

### 特定图片加载失败

如果上游图片存在重定向问题或不受支持的内容，图片会安全失败，而不是泄露用户的 IP。

Worker 会记录重定向链失败，使用省略查询字符串的已清理 URL，这有助于在不记录跟踪参数的情况下调试上游重定向循环。

### 应用仍直接加载图片

请再次确认：

- `NEXT_PUBLIC_IMAGE_PROXY_BASE_URL` 已设置
- 浏览器正在通过正常的 HTML 电子邮件查看器渲染邮件
- 你的代理主机名可从浏览器访问

## 推荐设置

对大多数自托管用户而言：

1. 正常部署主应用。
2. 选择一种代理模式：
3. 最简单：设置 `NEXT_PUBLIC_IMAGE_PROXY_USE_APP_ROUTE=true` 和 `IMAGE_PROXY_SIGNING_SECRET`。
4. 隔离性更强：在 Cloudflare Workers 上单独部署图片代理，并设置 `NEXT_PUBLIC_IMAGE_PROXY_BASE_URL` 加上 `IMAGE_PROXY_SIGNING_SECRET`。

应用内路由是最简单的自托管设置。当你需要更强的隔离或独立扩展时，单独的代理服务仍然是更合适的选择。
